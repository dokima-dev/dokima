> # The ask
> 
> The README tells adopters to put `DOKIMA_APP_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` in an Actions environment named `keys`. With the thin install (the adopter's `dokima.yml` calls `entry.yml@<tag>` in this repo, which calls the role workflows), those environment secrets never reach the jobs. A job like `uptodate / update` declares `environment: keys`, gets the repo variable `DOKIMA_APP_ID`, but its `secrets.DOKIMA_APP_KEY` is empty, so `create-github-app-token` fails with "privateKey option is required". A job defined in the adopter's own repo with `environment: keys` reads the same secrets fine, so the values are stored correctly; the cross-repo, nested call is what drops them. This repo never hit it because its workflows run locally, not through the thin install.
> 
> Repo-level secrets with the same names do reach the jobs through `secrets: inherit`.
> 
> **Ask:** make the documented setup work for adopters: say repo-level secrets in the README and install docs (or support both), and have the setup audit check for the secrets where the thin install can actually read them.
>
