> # The ask
> 
> An agent run loses all its work when the branch moved while it ran.
> 
> Seen on an adopter repo: plan review (one `dokima-next` run) blocked a plan and dispatched the next planner run before its own last pushes finished. The two runs overlapped by a few seconds. The planner ran four minutes, then its push to `try/issue-N` was rejected (`non-fast-forward`), and so was its push to the `logs` branch (`fetch first`). The issue got "The run's changes could not be saved to try/issue-N, so nothing it did is on the branch", and the run's work and log were thrown away.
> 
> Fix:
> - When a push of the run's branch or of `logs` is rejected because the remote moved, fetch, rebase the run's own commits onto the new tip, and push again (a few tries). Only if the rebase conflicts does the run fail, and then the record names the conflicting files.
> - The run that dispatches the next agent does so only after its own pushes have landed.
> - Tests: a fake remote that gains a commit mid-run still ends with the run's commit on top; the log push likewise; a real conflict still fails with the files named.
> ----
