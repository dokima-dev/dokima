**Agent:** The planner, worker and reviewer are all built around a plan. Nothing in the repo knows about `hotfix` yet, and a worker run with no approved plan fails at the pack step (details in section 2).

## 1. How the planner starts on autopilot
- The two lines are defined at `dokima/agent_autopilot.py:125-126`.
- `start_planner(repo, number, line)` (`agent_autopilot.py:413`) posts the line, then sends a `repos/{repo}/dispatches` event with `event_type=dokima-next` and `client_payload[role]=planner`, `[stage]=plan`, `[issue]=N`. That event triggers `agent.yml` (`repository_dispatch: dokima-next`, `.github/workflows/agent.yml:15`). `ROLE` and `STAGE` come from the payload (lines 51-53), and `STAGE` is only kept for the reviewer.
- `start_waiting(repo, numbers, line)` (`:423`) decides "start planner". It skips an issue that is not open, has sub-issues, has an open blocker, or `started_before` is true (`:401`, which checks for a bot record, live card or Autopilot line).
- `start_unblocked` (`:473`) and `plans_again` (`:453`) handle the "blockers merged" case. Both use the default line.
- Who calls them, all in `dokima/agent_roles.py`: `autopilot start` (`:669-671`, switched-on line), `labeled` (`:689`, `:695`), and stories after a split (`:445`).
- After any run, `next_step()` (`dokima/agent_next.py:109`) returns `("start", role, stage[, "autopilot"])`. `agent.py next` prints it, and the "Start the next stage" step dispatches the same event (`agent.yml:661-686`).

## 2. How the worker starts and what it reads
- `pack(repo, number, role, stage, dest)` is at `agent_roles.py:150`.
  - For the worker it returns False when `not approved(recs)` (`:173`), before writing `plan.json`.
  - `main pack` then exits 3 (`:315`). The workflow fails with "No passed plan on the issue yet, or (for the worker) no plan review approving the newest plan" (`agent.yml:324-330`).
- `NEEDS["worker"] = ["issue.md", "plan.json"]` (`:196`) is checked by `problems_pack` (`:201`). The reviewer's pr pack needs `plan.json` too (`:197`). `tests/test_agent.py:156` already asserts `"plan.json is missing"` for the worker.
- `agent.yml` has four more plan dependencies:
  - Starting branch: when `try/issue-N` is missing, a worker run fails with "run the planner first" (`agent.yml:302-307`). The planner normally creates that branch.
  - Check command: `check work $OUT/work.json $PACK/plan.json $N` (`:427`). `check()` (`dokima/agent_checks.py:423`) reports "plan.json is missing" through `load`. `problems_plan` (`:381`) requires one criteria line per plan criterion. `failing_plan_tests` (`:412`) runs the plan's tests.
  - Fence: `python3 -m dokima.fence "$BASE" "$PACK/plan.json"` (`agent.yml:476`). `dokima/fence.py:61` calls `json.load` on the plan, so it crashes without one. `scope_from` (`:17`) limits changes to the plan's files, so a "hotfix scope" would need a new rule.
  - Prompt: `python3 -m dokima.prompt ROLE GRADE` (`dokima/prompt.py:build`). The pack list text is at `agent.yml:438-446`. The worker prompt (`dokima/roles/worker.md:2-17`) assumes "one approved plan".

## 3. Code reviewer after the worker
- `next_step`: `role == "worker"` gives `("start", "reviewer", "pr")` (`agent_next.py:144-145`), dispatched as in section 1.
- The pack adds `diff.patch` (`agent.yml:331`) and the worker run (`agent_roles.py:186-189`).
- The check is `check review ... $PACK/plan.json $N` (`agent.yml:426`). `check()` runs `problems_boxes(data, plan_criteria(plan, number))` (`agent_checks.py:230`, `:371`), so the review is graded against the plan's criteria ids.
- `reviewer.md:15` says the reviewer reads "the planner's plan.json".
- `main record` loads `PACK/plan.json` to draw the review (`agent_roles.py:354-361`).

## 4. How the worker opens its PR
The PR is opened in shell, not Python: `gh pr create --draft --head try/issue-N --base $DEFAULT_BRANCH --title <issue title> --body "Closes #$N"` (`agent.yml:532-533`). It passes no `--label`. Later `card.pr_body()` (`dokima/card.py:637`) rewrites the body as the card plus the original issue, with no Closes line. `card.draw` calls it at `card.py:1024`. `tests/test_worker_pr.py` runs these real workflow steps and reads the calls with `Finish(tmp, role, change, pr_open).opened()` and `flag(call, "--label")`.
