> # The ask
> 
> v0.1.3 (#894) made the install file hand `DOKIMA_APP_KEY` and the agent keys to `entry.yml` by name. In a repo owned by a different account, the key now reaches `entry.yml`, but its inner jobs still get nothing. `entry.yml` calls its inner workflows (`uptodate.yml`, `agent.yml`, `commands.yml`, `assign.yml`, `autopilot.yml`, `board.yml`, `card.yml`, `audit.yml`) with `secrets: inherit`. When the run belongs to another account, `inherit` carries no secrets, the same as it did at the top level.
> 
> Seen on an adopter repo on `entry.yml@v0.1.3` with explicit mapping and repo secrets set:
> - `testmon / baseline` passes (it needs no secrets).
> - `uptodate / update` fails: `[@octokit/auth-app] privateKey option is required`, from `private-key: ${{ secrets.DOKIMA_APP_KEY }}`.
> 
> Fix: hand secrets over by name at every level, not only at the top.
> - Each inner workflow that reads a secret declares it under `on.workflow_call.secrets` (`DOKIMA_APP_KEY` required where it is used; agent keys optional).
> - `entry.yml` passes each one by name (`secrets: {DOKIMA_APP_KEY: "${{ secrets.DOKIMA_APP_KEY }}", ...}`) instead of `secrets: inherit`. Pass only the secrets each inner workflow declares.
> - Add a test that fails if any `uses: ./.github/workflows/...` call in `entry.yml` says `secrets: inherit`, or passes a secret its target workflow does not declare.
> - Release it as v0.1.4 (CHANGELOG heading), and point the install file at `@v0.1.4`.

**Agent:** I fixed the reviewer's blocker by changing an older test, `tests/test_keys.py`. The test's rule itself is unchanged. The four related test files pass (36 tests), and both hand-back checks pass. I didn't run the full suite, which runs at the merge gate.

**Why the test failed:** It requires every job that mentions a secret to sit in the "keys" environment, which only main can open. Passing secrets by name, as the ask requires, puts secret names on jobs that call another workflow. GitHub doesn't let those jobs name an environment, so the test failed on all eight such calls in `entry.yml` and on the one in `commands.yml`. The reviewer only named the `commands.yml` one.

**The change:** On a job that calls another workflow, the test now ignores the one line that passes secrets on by name. Any other mention of a secret on such a job still fails. The jobs that actually use a key still have to be in the "keys" environment, and they are. Per GitHub's docs, when a called job sits in an environment, that environment's secrets win over the ones passed in. So Dokima's own repo still takes its keys from the safe, and the ask's explicit passing doesn't weaken that.

The workflow general rules say never to edit a test, but the hotfix rules allow changing a small one. The reviewer should know this round touched an existing test.

The hand-back marks [#897](https://github.com/dokima-dev/dokima/issues/897) (inner workflows get no secrets in another account's repo) blocker R1 as done. It is in `/tmp/dokima-out/work.json`.
