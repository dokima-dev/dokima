**Agent:** I planned [#617](https://github.com/dokima-dev/dokima/issues/617) (a split approved again files nothing) as a single user story. Both hand-back checks pass. The new test fails on today's code for the right reason: the re-approved split files no new stories.

**The cause:** once a parent's first split is filed, `file_split()` in `dokima/agent.py` returns that old filing record on every later call. So when the owner rescopes the parent and approves a new split, nothing new gets filed.

**Plan:**
- **Title:** A re-approved split files its new stories
- **617.1:** A split approved after its earlier stories were filed files its new stories as sub-issues.
- **Edge case:** filing the same approved re-plan a second time files nothing more.
- **Scope:** `dokima/agent.py` only.
- **Links:** relates to [#553](https://github.com/dokima-dev/dokima/issues/553) (extra criteria go to a new sibling story).
- **Raises:** none, and there were no open blockers to answer.

**Test:** I added `test_a_split_approved_after_its_stories_were_filed_files_its_new_stories` to `tests/test_agent.py`. It files a first split, then approves a re-plan with a different story, and checks three things:
- the new story is created;
- the old filing record is not handed back;
- filing the re-plan again creates nothing more.

**One thing the worker will need to handle:** the `split` command only posts a new filing record when no earlier one exists, unless it is editing the queued card (`CARD_ID`). Normally that card is there. If it isn't, the second filing leaves no record, so a later `/work` could file the same stories twice. The fix in `dokima/agent.py` should cover this, but the plan has no separate criterion for it.

The plan is in `/tmp/dokima-out/plan.json`. The test file change is not committed.
