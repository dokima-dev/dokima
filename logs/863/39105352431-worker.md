**How it works:**
- **Which issues count:** an issue is a hotfix while it has the label and no planner has run on it. Once code review sends it back to planning, it follows the normal flow.
- **Starting:** a code owner's `/work` starts the worker on a new branch from main. On autopilot, an unblocked hotfix starts its worker instead of its planner, with its own line, "Autopilot: blockers merged, starting work" (or "switched on, starting work").
- **The pack:** the worker and the code reviewer get `ask.md`, the issue's text as the whole ask, and no plan. Their prompts get a short hotfix section, which other runs leave out.
- **Changes stay:** for a hotfix, nothing the worker writes is dropped, tests included.
- **Checks:** the worker's and reviewer's hand-backs are checked by their shape only, since there's no plan. The pull request gets one "Hotfix: all tests pass" check, then the usual merge gate. A red required check still fails the gate and sends it back to the worker.
- **Back to planning:** when code review finds the change bigger than the ask, the planner starts and the issue gets a comment giving the reviewer's reason.

The new logic is in a new file, `dokima/hotfix.py`. The rest are small changes to the workflow, the pack builder, the autopilot code, the merge check, the fence and the two role prompts.

**Changes along the way:**
- I first added a hotfix label setting to the defaults. An older test pins the exact list of default labels, so I took it out. The code just uses the name `hotfix` unless a repo names its own.
- Some older tests use a fake GitHub that fails on any call they don't expect. So the workflow reads the label once, before the pack, instead of the pack asking GitHub.
- Another older test expects the plan file path to appear word for word in the check command. So that line stays as it was, and a hotfix run swaps in `-` afterwards.
